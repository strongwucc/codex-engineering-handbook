# 为开发项目配置 Codex

为目标仓库提出最小、可验证、适合团队协作的 Codex 配置。先区分用户要的是建议还是实际修改；不要把个人习惯、可选功能或未经验证的版本行为变成团队默认项。

## 适用范围

- 新建项目时规划 Codex 配置，或为现有仓库补齐、审查项目级 Codex 配置。
- 不用于单纯理解陌生代码库或沉淀架构上下文；这类任务使用 `deep-init`。
- 不把本 Skill 所在的个人全局目录误当作项目配置。个人 Skill 通常只影响当前用户；提交到仓库的指令、Skill、Hook 和配置会影响团队使用者。

## 先了解项目

1. 确认仓库根目录和当前未提交改动；写入前查看 `git status --short`，保留已有改动。
2. 定向检查现有 `AGENTS.md`、`AGENTS.override.md`、`.codex/`、`.agents/skills/`，以及 README、依赖清单、CI 和现有测试/格式化命令。不要为配置建议扫描或输出密钥、环境文件及用户配置内容。
3. 确认语言与框架、开发和验证流程、Codex 的主要用途、需共享还是仅个人使用，以及现有审批和安全边界。只在答案会改变配置时追问。
4. 记录 `codex --version`；对易变设置先用当前 CLI 帮助和官方文档核对，不凭记忆编造配置键、默认值或行为。优先参考 `/Users/chuanchuan/Work/codex/docs/principles.md` 和 `docs/configuration/` 中相关主题；如事实需联网核验，使用 `web-access` Skill 打开官方原文。

## 选择最小配置

- **项目指令**：用根目录 `AGENTS.md` 写稳定、全队适用的仓库约定、重要边界和真实验证命令；只在子目录确有不同规则时增加局部指令。保持入口简短，链接到已有文档而不是重复整本手册。
- **项目设置**：仅当配置能稳定提升该仓库的体验，且当前 Codex 版本与项目共享边界支持时，才建议 `.codex/config.toml`。机器、账户、认证、个人 profile 或其他不适合提交的设置留在用户层；不要为了减少确认而放宽沙箱或审批。
- **共享 Skills**：仅将可重复、项目相关的工作流放入仓库支持的 `.agents/skills/`；个人工作流留在用户级目录。先检查是否已有等价 Skill，避免重复和同名歧义。
- **自定义 Agent**：只有存在稳定、可区分且重复使用的专门角色时才引入；不能把 Agent 当作权限隔离或独立工作树的保证。
- **Hooks**：只有明确需要自动执行的检查且收益高于维护成本时才建议。提交或启用前审查脚本来源、命令、输入、权限、超时和输出；不得让 Hook 输出秘密，也不得把 Hook 当唯一安全边界。
- **多 Agent**：默认不启用额外编排。仅在任务可并行、边界不重叠且预期收益足以抵消成本时建议；优先并行只读工作，多个 Agent 同时写入需有明确隔离和冲突处理方案。

配置层级、支持字段和信任行为可能随 CLI 版本变化。涉及具体设置时，按知识库中的 `configuration-hierarchy.md`、`agents-md.md`、`permissions-and-sandbox.md`、`skills.md`、`hooks.md` 或 `multi-agent.md` 查对应主题，并回到当前官方文档核实易变事实。

## 提案与修改边界

- 用户只问“怎么配置”或要配置建议时，只给分层方案，不改仓库文件。
- 用户明确要求实际配置时，只修改授权范围内、确有必要的项目文件；不擅自改个人全局设置、组织策略、审批/沙箱强度、Hook 或敏感文件。涉及安全边界或会影响团队的实质选择，先说明影响并取得确认。
- 提案说明当前状态、推荐项、暂不推荐项、文件作用范围（个人/项目团队）、收益与代价，以及每项的验证方式。优先复用已有规则和文档，不为“完整”而添加空目录、样板、Hook 或多 Agent 配置。

## 验证与交付

1. 对照当前官方配置文档和已安装 CLI 核对新增字段；区分静态格式检查与真实运行验证。
2. 只运行与变更相关、无破坏性的检查。验证指令发现或 Hook 行为时，使用隔离、无敏感数据的测试项目；不要用危险命令测试权限边界。
3. 审阅最终 diff，检查路径、作用范围、秘密泄露和未授权改动。报告变更文件、为何需要、是否会影响团队、执行的验证及 `not_run` 项；未实测不得声称运行时行为已验证。
