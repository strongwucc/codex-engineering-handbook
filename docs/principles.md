# 稳定工程原则

本文只收录跨模型、跨版本仍可复用的 Harness 工程原则，不描述 Codex 当前配置键、默认值、命令参数或产品行为，也不代表 OpenAI 官方评分或规范。后续如出现反例，应更新原则及其适用边界，而不是把单次经验改写成普遍定律。

## P1：让仓库成为可追溯的事实源

- **原则**：把项目规则、决策和维护入口保存在仓库中，并将导航与详细知识分开。
- **解决的问题**：聊天记录、个人记忆和零散文件难以协作复用，也无法稳定复核。
- **适用条件**：规则需要跨会话、跨成员或跨评估复用时。
- **不适用条件**：短期、一次性的任务偏好不必沉淀为项目规范。
- **支持证据**：OpenAI 的 Harness 工程案例把结构化仓库知识作为事实源，并用简短的 `AGENTS.md` 导航到正文。[source:OAI-HARNESS-2026]
- **可执行检查**：检查关键决策是否有仓库内文档入口；规范性外部主张是否引用 `sources/registry.yaml` 中的来源 ID；运行 `scripts/verify-knowledge-base.sh`。
- **已知反例或限制**：仓库文档仍可能过期或缺失；它是可复核的事实源，不等同于运行时状态，也不能替代版本核验。

## P2：指令文件做地图，不做百科

- **原则**：让入口指令保持短小、可执行，并将主题细节放入有边界的专题文档。
- **解决的问题**：冗长、重复的指令会模糊优先级，并增加维护和检索成本。
- **适用条件**：规则需要在多个任务中被发现或遵循时；详细规则可按需链接加载。
- **不适用条件**：不能为追求简短而删除安全边界、关键约束或必要的局部规则。
- **支持证据**：OpenAI 的 Harness 工程案例和 Codex 指令文档建议将 `AGENTS.md` 作为地图，并保持内容实用、聚焦。[source:OAI-HARNESS-2026] [source:OAI-CODEX-BEST-PRACTICES] [source:OAI-AGENTS-MD]
- **可执行检查**：根指令优先列出项目地图、关键约束和验证命令；检查详细内容是否有专题文档承载、入口是否指向有效路径。
- **已知反例或限制**：文档拆分过度也会增加跳转成本；高频且必须始终生效的规则不应藏在深层链接中。

## P3：把确定性约束转成机械检查

- **原则**：能稳定判定的格式、引用、路径和回归要求，优先用脚本或测试验证；把运行时行为另行实测。
- **解决的问题**：纯文字约定容易漂移，人工重复检查也容易遗漏；静态扫描则无法证明真实运行行为。
- **适用条件**：判定条件明确、可重复，且检查成本低于持续人工核对时。
- **不适用条件**：需要语义判断、真实权限或交互环境的行为，不能只靠静态规则给出通过结论。
- **支持证据**：OpenAI 的 Harness 工程案例描述了使用机械检查和周期性文档维护来约束仓库质量。[source:OAI-HARNESS-2026] 本仓库将具体检查范围和通过门槛定义为本仓库治理决策，以减少可预防的文档与评估漂移。
- **可执行检查**：先写清可判定条件，再运行针对性检查；报告分别记录静态检查、自动化测试和实际行为观察，不用其中一种替代其他证据。
- **已知反例或限制**：机械检查可能漏掉语义错误，也可能因规则过宽产生误报；检查器本身需要测试和维护。

## P4：在目标任务和环境中评估端到端结果

- **原则**：评估 Agent 或 Harness 时，使用能观察任务完成过程与结果的代表性任务，不只审阅配置或提示文本。
- **解决的问题**：静态材料看起来完备，不代表系统能在目标仓库、工具和执行环境中正确完成工作。
- **适用条件**：系统行为依赖多步推理、工具交互、代码编辑或执行环境时。
- **不适用条件**：单纯检查文档结构、来源登记等确定性属性时，静态检查更直接；不应为每个低风险文字变更都运行完整端到端评测。
- **支持证据**：AgentBench 在多个交互环境中评估 Agent；SWE-bench 使用真实 GitHub issue 和仓库代码评估问题解决能力。[source:A-AGENTBENCH-2024] [source:A-SWE-BENCH-2024]
- **可执行检查**：从目标工作流抽取可复现任务，记录输入、环境、工具边界、验收条件和实际验证结果；未执行的项目标记 `not_run`，环境阻断标记 `blocked`。
- **已知反例或限制**：基准任务只是目标工作的样本；基准得分不能直接推出对其他仓库、模型或工具环境的表现。

## P5：比较结果时同时限定实验条件

- **原则**：报告评测结论时一并记录任务集、模型、Harness、样本、指标和环境；只在条件足够接近时比较结果。
- **解决的问题**：遗漏实验条件会把局部结果误读为普遍能力或架构优劣。
- **适用条件**：横向比较模型、Agent 架构、工具配置或版本回归时。
- **不适用条件**：目标只是验证单个仓库内预先定义的验收条件时，不需要包装成跨系统排行榜。
- **支持证据**：AgentBench 与 SWE-bench 使用不同任务和环境；LangChain 的多 Agent 文章只报告其改造后的 τ-bench、GPT-4o 和特定 retail 样本设置下的实验。[source:A-AGENTBENCH-2024] [source:A-SWE-BENCH-2024] [source:B-LANGCHAIN-MULTIAGENT-2025]
- **可执行检查**：报告中固定记录模型与版本、Harness 配置、任务和样本范围、工具/执行环境、指标及变更；结论文字不得超出该范围。
- **已知反例或限制**：完整记录条件仍不能消除样本偏差、测量误差或不可复现因素；跨基准分数通常不具备直接可比性。

## P6：把基准本身也纳入质量审查

- **原则**：评测前检查任务是否泄露答案、验收测试是否能区分正确与错误结果，并将疑点作为限制报告。
- **解决的问题**：任务泄漏或薄弱测试可能让评测成绩与真实任务能力脱钩。
- **适用条件**：使用自动评分、公开基准、由 issue 与补丁构造的任务，或复用现成测试作为验收标准时。
- **不适用条件**：来源或测试存在疑点时，不应据此断言整个基准无效；应说明审查范围并继续寻找独立证据。
- **支持证据**：SWE-Bench+ 作者预印本报告了对特定 SWE-Agent/GPT-4 样例的人工审查，并指出其中存在答案泄漏和测试质量风险；该研究尚登记为作者原始预印本，其结果不外推为 SWE-bench 的普遍发生率。[source:A-SWE-BENCH-PLUS-2024]
- **可执行检查**：抽查任务描述、补丁与测试之间的信息泄漏；用已知正确和错误结果验证测试区分能力；记录抽查样本、方法和限制。
- **已知反例或限制**：人工审查会受样本和审查者判断影响；此处证据来自预印本中的特定审查，不能替代对当前评测集的独立审计。

## P7：只有测得收益后才引入额外编排

- **原则**：增加多 Agent 或其他编排层之前，先定义单 Agent 基线、目标指标和复杂度成本，再用目标任务实测是否值得。
- **解决的问题**：架构复杂度、Token 消耗和故障面可能增长，却未改善目标任务结果。
- **适用条件**：考虑拆分角色、引入 supervisor、并行 Agent 或改变控制流时。
- **不适用条件**：已有明确的隔离、权限或吞吐需求，且单 Agent 结构无法满足时；此时仍要验证实现是否满足需求。
- **支持证据**：LangChain 的一手实验比较了单 Agent、swarm 和 supervisor，但测试仅覆盖其改造后的 τ-bench、GPT-4o 与有限 retail 样本；本文只据此支持“需要在目标设置下比较”的方法，不声称某一架构普遍更优。[source:B-LANGCHAIN-MULTIAGENT-2025]
- **可执行检查**：保留可比的基线，预先指定任务成功条件与资源指标，重复运行并记录方差来源；将收益和维护成本一起评审。
- **已知反例或限制**：特定架构在狭窄任务上胜出不保证跨任务复现；安全隔离和组织边界等要求也不能简化为 Token 或成功率比较。
