# 面向任务的上下文

本专题连接[稳定原则](principles.md)和[评估标准](evaluation-standard.md)，用于审视任务需要的信息如何被发现、核验、使用和反馈。下述流程是本仓库的工程建议，不是 Codex 产品行为保证，也不是收益已被证明的通用方法。

## 思路与证据边界

Andrej Karpathy 是 AI 研究者，曾参与开发和使用编程 Agent；他在个人回顾中将上下文工程列为 LLM 应用的职责，并描述 Agent 将推理和工具使用连接成循环。[source:B-KARPATHY-REVIEW-2025] 他将上下文视为影响模型工作的杠杆，并以观察环境和处理反馈为例；该访谈整理由 AI 生成，作者称已阅读。[source:B-KARPATHY-SEQUOIA-2026] 他也将上下文学习描述为运行时适应，并讨论基于文本而非权重的记忆。[source:B-KARPATHY-ANIMALS-2025]

以上是作者观点和实践语境，不能证明某个 Codex 版本的加载语义、某种组织方式的普遍收益，或模型已修改权重。Codex 产品事实以已核验的 OpenAI 来源为准；实际效果须在目标任务与环境中评估。

## 从任务到反馈

1. **任务与边界**：识别本次目标、授权、适用约束和验收条件；不要将其他任务的偏好自动当作本次授权。
2. **发现与适用**：从项目地图查找相关规范、专题、Skill 和代码；根据目录、任务及实际可用性判断其适用范围。关键边界保留在应持续生效的入口，不为简短而隐藏。
3. **核验与取舍**：区分项目文档、用户提供的信息、历史记忆、当前代码/环境与外部原文。按需读取足够支撑下一步的资料；文档可能过期，当前状态和易变外部事实需按任务范围核对。不要为控制长度删去必要证据或约束。
4. **执行与反馈**：依据任务授权使用工具，读取相关结果并调整判断；区分命令存在、实际运行及执行结果。证据不足时说明未知或阻塞，不将推断写成现场事实。
5. **记录与复用**：需要跨会话保留的信息应可追溯、具有维护入口和适用范围；单次任务记录不自动变成长期规则。不要把用户私有记忆当成仓库已经包含的事实。

示例：审查退款渠道时，先找业务规则，再追踪实际调用和订单字段；若历史订单数据不可访问，报告这部分未验证，不猜测历史订单一定符合规则。文档能找到不等于本次会话已经读取或理解它。

## 如何检查是否有效

静态检查适合确认链接和格式；独立会话任务可观察规则发现、证据引用、冲突处理、实际结果与未验证项。使用 [H11 任务](../evals/fixtures/H11-context-discovery.md) 时，按[评估者隔离协议](../evals/holdout.md)准备合成项目并保存运行证据。单次通过只说明该次任务的结果，不能证明所有项目或模型都有效；对照实验应固定任务、模型、环境和工具边界，记录失败与成本。
