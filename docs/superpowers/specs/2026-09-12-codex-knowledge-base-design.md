# Codex 最佳实践知识库设计规格

## 1. 目标

在 `/Users/chuanchuan/Work/codex` 建设一个可版本化、可追溯、可验证的 Codex 最佳实践知识库，作为以下工作的唯一事实源：

- 解释 Codex Harness 的稳定工程原则；
- 提供经过当前官方文档核验的项目配置教程；
- 使用统一标准评估项目的 Codex Harness 成熟度；
- 在 Codex、模型或官方配置发生变化时定位并更新受影响内容；
- 用回归型评测验证规则是否真的改善正确性、安全性和可维护性。

知识库不是 Codex 百科，也不收录无法追溯的社区经验汇编。它只保存能够指导工程决策、能够说明适用边界、并能被证据复核的结论。

## 2. 成功标准

首版知识库完成时必须满足：

1. 每个外部事实和技术结论都有 `[source:ID]`；来源等级、复核周期和流程门槛等内部治理决策标明为本仓库治理决策并说明治理理由，不伪造外部背书；
2. 每个来源都记录作者或机构、标题、日期、原始链接、来源等级、核验日期和适用范围；
3. Codex 的配置键、默认值、Hook、权限和模型行为只以 OpenAI Docs 或 OpenAI 官方源码为事实依据；
4. 工程原则至少有一项官方实践、权威技术论文或合格专家一手分享支持；
5. 评分标准中的每个维度都有可观察证据和明确的 1/3/5 星锚点；
6. 配置教程中的命令和配置片段能够被当前可用的 Codex CLI 或官方 schema 验证；
7. 文档链接、来源登记、引用完整性和过期状态能够被脚本检查；
8. 知识库不依赖相邻的 Claude Code 目录才能读懂或运行；
9. 自动维护只生成报告或待审改动，不自动执行 `git add`、`git commit` 或 `git push`。

## 3. 设计原则

### 3.1 仓库是唯一事实源

OpenAI 的 Harness Engineering 实践将结构化的仓库内文档作为 system of record，并让简短的 `AGENTS.md` 充当目录，而不是把全部知识塞入上下文。该实践同时强调交叉链接、结构检查和周期性 doc gardening。[^openai-harness]

本知识库采用相同边界：

- `README.md` 和 `AGENTS.md` 负责导航；
- `docs/` 保存解释性和规范性正文；
- `sources/` 保存来源与声明之间的映射；
- `evals/` 保存可重复评测；
- `scripts/` 只实现确定性校验；
- 版本相关事实不得只存在于聊天、Memory 或个人经验中。

### 3.2 稳定原则与易变事实分离

稳定原则包括最小权限、证据化验证、上下文节制、机械化约束和人类负责最终判断。易变事实包括模型名称、配置键、默认值、Hook 事件、命令参数和产品能力。

稳定原则放入 `docs/principles.md`；易变事实放入 `docs/platform/`。后者必须携带核验日期和适用版本，防止模型或 CLI 升级后旧结论继续被当作当前事实。

### 3.3 指令是地图，不是百科全书

根 `AGENTS.md` 只包含知识库地图、来源纪律、维护命令和禁止事项。OpenAI Docs 建议将 `AGENTS.md` 保持简短、实用，并从重复发生的真实问题中增量更新；目录级指令用于局部规则。[^openai-best-practices][^openai-agents-md]

### 3.4 重要约束必须可执行

仅写“保持文档新鲜”无法验收。对应约束必须落入确定性检查：

- 没有 `[source:ID]` 的外部事实或技术结论失败；未标明为本仓库治理决策并说明理由的治理规则失败；
- 易变来源超过复核期限后失败；
- 来源 URL 无法访问时报警；
- 教程引用不存在的配置键时失败；
- 评估报告混淆项目级和用户全局能力时失败。

## 4. 来源准入制度

### 4.1 来源等级

| 等级 | 来源 | 可支持的结论 | 限制 |
|---|---|---|---|
| S | OpenAI Docs、OpenAI 官方源码、OpenAI 官方发布说明、OpenAI 官方系统卡 | Codex 当前能力、配置、默认行为、安全边界、模型事实 | 易变事实必须记录核验日期和版本 |
| A | 同行评审论文、顶级会议论文、作者发布的原始预印本、正式技术标准 | 评测方法、Agent 架构、软件工程和安全机制 | 必须核对研究对象、实验条件和外推边界 |
| B | 领域公认专家或一线系统作者的原始技术文章、演讲、访谈、设计记录 | 实践模式、失败经验、设计权衡、待验证假设 | 不得单独证明 Codex 当前配置或产品行为 |
| X | 搜索摘要、聚合文章、转载、营销软文、匿名帖子、无原始出处内容 | 只能用来发现一手来源 | 不得进入正文引用或评分依据 |

### 4.2 “大牛技术分享”的准入条件

专家分享必须同时满足：

1. 作者身份可核验：系统作者、核心维护者、论文作者或长期公开贡献者；
2. 内容来自作者本人或主办方发布的原始文章、视频、播客或演讲稿；
3. 内容包含可复核的机制、案例、数据或明确经验边界，而不是只有观点；
4. 记录作者与主题的直接关系，解释为什么该作者在此结论上具有权威性；
5. 观点与官方事实冲突时，以官方事实为准，并显式记录冲突。

“知名”本身不是证据等级。专家分享用于补充实践语境，不能替代官方配置文档或实验论文。

### 4.3 声明级引用

来源管理的最小单位是“声明”，不是整篇文档。每个外部事实或技术结论，尤其是会影响操作、评分或安全判断的句子，都要关联一个或多个 `[source:ID]`。来源等级、复核周期和流程门槛属于本仓库治理决策，必须明确标注并说明治理理由，不得伪造外部背书。

来源登记建议使用以下字段：

```yaml
id: 'OAI-HARNESS-2026'
level: 'S'
publisher: 'OpenAI'
authors:
  - 'Ryan Lopopolo'
title: 'Harness engineering: leveraging Codex in an agent-first world'
published_at: '2026-02-11'
verified_at: '2026-09-12'
url: 'https://openai.com/index/harness-engineering/'
applies_to:
  - 'Codex engineering workflow'
stability: 'stable'
claims:
  - 'repository knowledge as system of record'
  - 'AGENTS.md as a map rather than a monolithic manual'
status: 'active'
```

### 4.4 证据冲突处理

来源冲突时按以下顺序处理：

1. 同一产品事实优先采用更新的 OpenAI Docs 或官方源码；
2. 论文结论仅在相同任务、模型、Harness 和指标范围内比较；
3. 官方案例与独立研究冲突时并列呈现实验条件，不用权威等级抹平差异；
4. 无法消解的冲突标记为 `contested`，不得写成确定性建议；
5. 已被官方废弃或更新的来源标记为 `superseded`，保留迁移价值但退出当前推荐。

## 6. 核心文档职责

### 6.1 `docs/principles.md`

只收录跨模型、跨版本仍然成立的工程原则。每条原则采用统一结构：

- 原则；
- 解决的问题；
- 适用条件；
- 不适用条件；
- 支持证据；
- 可执行检查；
- 已知反例或限制。

### 6.2 `docs/evaluation-standard.md`

保留九个维度：任务与自主性、上下文、架构约束、熵管理、安全、测试验证、CI/CD、Agent 编排、透明度与可复现性。

每个维度必须提供：

- 检查对象；
- 项目级、用户全局、当前有效、可移植性四层证据；
- 1/3/5 星锚点；
- 不能由静态扫描确认的项目；
- 生产级硬门槛；
- 对应 holdout 用例。

总体等级不能用平均分机械决定。安全低于 4 星、测试或 CI/CD 低于 3 星时，不得评为生产级。缺失证据写“未发现机械证据”，环境失败写 `blocked`，均不得视为通过。

### 6.3 `docs/configuration/`

每篇教程采用相同格式：

1. 使用场景；
2. 官方语义；
3. 最小配置；
4. 配置层级与覆盖规则；
5. 安全边界；
6. 验证命令；
7. 常见失败；
8. 版本与最后核验日期；
9. 官方来源。

教程不得把当前机器的个人配置直接包装成通用推荐。示例中不得包含真实用户名、密钥、Token、生产地址或不可移植绝对路径。

### 6.4 `evals/`

首版沿用并重新核验以下任务类型：

- 精准修改；
- 只读审查；
- 验证诚信；
- 敏感信息边界；
- 危险命令；
- 指令冲突；
- Skill 触发准确性；
- 多 Agent 写入隔离；
- 模型升级回归；
- 配置教程兼容性。

每项记录成功率、耗时、Token、审批次数、越界文件数、验证真实性和测试环境。被测 Agent 不得看到期望答案。

## 7. 维护流程

### 7.1 更新触发器

- 每月：检查 OpenAI Docs、Codex 发布说明、官方源码 schema 和失效链接；
- 模型或 Codex CLI 大版本发布：立即执行完整升级审计；
- 官方文档修改配置、权限、Hook 或 Skill 语义：立即复核相关教程；
- 项目评估连续发现同类缺口：评估是否补充原则、模板或 holdout；
- 专家分享或论文只进入候选池，不自动改变规范。

### 7.2 更新流水线

```text
发现候选来源
  → 验证原始出处与作者
  → 判断来源等级和适用边界
  → 拆分为声明级证据
  → 建立受影响文档清单
  → 更新正文、教程、模板和评测
  → 运行确定性检查
  → 人工审阅 diff
  → 经明确授权后再执行 Git 写操作
```

### 7.3 新鲜度规则

| 内容 | 默认复核周期 | 额外触发器 |
|---|---:|---|
| 模型、配置键、默认值、Hook、权限 | 30 天 | Codex 或文档发布变更 |
| 官方工程实践 | 90 天 | 官方文章修订或新案例 |
| 论文结论 | 180 天 | 新版本、复现研究或撤稿 |
| 稳定工程原则 | 365 天 | 评测出现反例 |

超过周期不等于自动错误，但状态必须变为 `review_due`，不能无提示地继续作为当前配置事实。

## 8. 首版迁移边界

现有 `codex-best-practices-research.md` 和 ClaudeCode 下的 Codex 知识库都只能作为候选材料，不能整体复制。

迁移一条内容前必须完成：

1. 找到其原始来源；
2. 打开并核验原文，而不是依赖旧文档的转述；
3. 判断事实是否仍适用于当前 Codex；
4. 将稳定原则与版本事实拆开；
5. 补充适用边界和验证方法；
6. 登记来源后再进入正式文档。

未通过上述步骤的内容留在研究笔记中，不进入规范层。

## 9. 验证设计

首版校验脚本只承担确定性工作：

- Markdown 内部链接存在；
- 来源 ID 唯一且被登记；
- 规范性文档引用的来源 ID 存在；
- `verified_at`、`stability`、`status` 字段完整；
- 易变来源是否超过复核期限；
- 不存在 `TODO`、`TBD`、空引用和示例密钥；
- 配置教程标注了适用版本和验证状态。

配置兼容性需要真实 Codex CLI 或官方 schema。若当前环境无法执行，必须报告 `blocked`，不得把 Markdown 语法检查写成“配置已验证”。

## 10. 分阶段交付

### 第一阶段：可信骨架

- 根导航与 `AGENTS.md`；
- 来源准入政策和 `registry.yaml`；
- 维护规则；
- 最小验证脚本；
- 将本设计引用的官方来源登记为首批 S 级来源。

### 第二阶段：核心内容

- 稳定原则；
- 项目评估标准；
- H1-H10 holdout；
- 评估报告模板。

### 第三阶段：配置教程

- `AGENTS.md`；
- 配置层级；
- 权限与沙箱；
- Hooks；
- Skills；
- 多 Agent。

每篇教程独立核验和交付，避免一次性迁移造成来源污染。

### 第四阶段：持续维护

- 新鲜度检查；
- 官方发布差异记录；
- 模型升级 core/profile holdout；
- 月度审计报告。

## 11. 非目标

首版明确不做：

- 自动发布网站；
- 自动提交或推送 Git；
- 自动采信搜索摘要或社区热门观点；
- 为所有语言和框架提供项目模板；
- 复制完整 OpenAI Docs；
- 用单个模型跑分替代真实项目评估；
- 将个人偏好包装成行业共识。

## 12. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 官方文档快速变化 | 易变事实独立存放，30 天复核和发布触发审计 |
| 权威光环替代证据 | 声明级引用，记录实验条件和适用边界 |
| 旧库错误被整体迁移 | 逐条回到原始来源，不直接复制规范内容 |
| 文档很多但无法执行 | 每项规范绑定检查或 holdout |
| 维护自动化扩大副作用 | 默认只生成报告和待审 diff，Git 写操作需明确授权 |
| 知识库挤占 Agent 上下文 | `AGENTS.md` 只做地图，正文渐进式加载 |

## 13. 决策记录

- 当前目录是 Codex 知识库唯一事实源；
- ClaudeCode 下的旧 Codex 库是迁移输入，不是持续同步目标；
- Markdown + YAML + Shell 是首版技术栈；
- 平台事实以 OpenAI Docs 或官方源码为准；
- 论文用于支持可泛化机制，专家分享用于解释实践经验；
- 外部事实和技术结论必须具备声明级可追溯性；内部治理决策必须标明为本仓库治理决策并说明理由；
- 自动维护不包含未经授权的 Git 写操作。
